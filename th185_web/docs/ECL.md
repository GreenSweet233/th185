# TH185 ECL 脚本格式（SCPT / ECLH）

> 状态：**容器结构与指令流已完全解出；81 种操作码的语义未解。**
> 日期：2026-11-11

---

## 1. 概览

`th185.dat` 里有 **114 个 `.ecl`** 文件，使用 **SCPT** 容器格式——
这正是 TH18 及之后作品的 ECL 格式，与 thcrap 的 `ThModern_ECLGetSub` 一致。

```
.ecl (SCPT)
  ├─ 头部（魔数 + 版本 + 名字数 + 子程序数 + 段标记）
  ├─ 子程序偏移表（34 项）
  ├─ 名字表（明文 ASCII）
  └─ 每个子程序：ECLH 块
       └─ 指令流（[id][size][rank][argc][payload]）
```

---

## 2. SCPT 容器

### 2.1 头部

```c
struct ScptHeader {
    char     magic[4];      // +0x00  "SCPT"
    uint32   version;       // +0x04  0x00100001
    uint32   name_count;    // +0x08  default.ecl = 36
    uint32   reserved0;     // +0x0C
    uint32   sub_count;     // +0x10  default.ecl = 34
    uint32   reserved1;     // +0x14
    uint32   reserved2;     // +0x18
    uint32   reserved3;     // +0x1C
    uint32   reserved4;     // +0x20
    char     anim_tag[4];   // +0x24  "ANIM"
    uint32   reserved5;     // +0x28
    char     ecli_tag[4];   // +0x2C  "ECLI"
    uint32   reserved6;     // +0x30
    uint32   sub_offsets[sub_count];  // +0x34
    // 随后是名字表（NUL 结尾字符串）
};
```

## 3. ECLH 子程序块

### 3.1 结构

```c
struct EclhBlock {
    char     magic[4];      // +0x00  "ECLH"
    uint32   header_size;   // +0x04  16
    uint32   reserved0;     // +0x08
    uint32   reserved1;     // +0x0C
    uint32   reserved2;     // +0x10
    // +0x14（tag 后 20 字节）开始是指令流
};
```

### 3.2 指令格式

```c
struct Instruction {
    uint16 id;      // 操作码
    uint16 size;    // 含本头的总长度
    uint16 rank;    // 推测：执行层级 / 优先级
    uint16 argc;    // 推测：参数个数
    uint8  payload[size - 8];
};
```

最初以为偏移表固定在 `+0x34`，结果**只有 `default.ecl` 能解析**。

对比两个文件：

```
default.ecl  +0x24  "ANIM" 00 00 00 00            ← 无动画名
             +0x2C  "ECLI" 00 00 00 00
```

## 9. ★ 内置函数表（本轮重大发现）

### 9.1 位置

**VA `0x43ECF4`**（`.text` 段内），**117 项**函数指针。

这是 ECL 解释器的**内置函数分派表**：脚本调用 `builtin(N)` 时，
解释器查表跳到第 N 个 thunk 执行。

### 9.2 调用约定

全部是 `__thiscall`：`ecx` = ECL 上下文对象指针，返回值在 `eax`。

绝大多数 thunk 是**纯字段读取器**，所以这张表同时是 **ECL 上下文布局图**。

## 10. ★ 内置函数分派器（本轮解出）

### 10.1 分派代码

**RVA `0x3E586`**：

```asm
03E586: mov eax, dword ptr [ebp + 8]      ; builtin 索引参数
03E589: sub esp, 8
03E58C: add eax, 0x2710                   ; ★ 基址 10000
03E591: cmp eax, 0x6e                     ; ★ 上限 110
03E594: ja 0x3ecea                        ; 超限 -> 返回 0
03E59A: jmp dword ptr [eax*4 + 0x43ecf4]  ; ★ 跳转表
```

### 10.2 关键结论

| 项 | 值 |
|---|---|
| builtin 编号基址 | **10000**（`0x2710`） |
| builtin 编号上限 | **10110**（`10000 + 110`） |
| 有效 builtin 数 | **111** |
| 表索引 | `N - 10000` |
| 表总项数 | 117 |
| 不可达项 | 111..116（超出 `cmp 0x6e` 上限） |

**表 117 项中只有前 111 项可达。** 而不可达的 111..116 恰好是
`push 2; push 2`、`push 6; push 3` 这类**成对参数辅助函数**——
它们不是 builtin，而是被其他代码直接调用。

### 10.3 这解决了一个疑问

上一轮我把表里的 117 项都当作 builtin，但索引 111..116 的实现看起来
与其余项风格不同（都是 `push imm; push imm` 而非读取字段）。
现在明白了：**它们超出 `cmp 0x6e` 的范围，本来就不是 builtin。**

### 10.4 调用链

```
ECL 脚本: builtin(10042)
     ↓
分派器 0x3E586: eax = 10042 + 10000? 不，是 eax = 42
```

等等——`add eax, 0x2710` 是**加上** 10000，不是减去。
所以参数是 **负偏移**？重新理解：

| 可能解释 | 说明 |
|---|---|
| A | 参数 `[ebp+8]` 是相对基址的**负**值（如 `-10000`），加上 10000 得 0 |
| B | 参数本身就是 builtin 编号，但解释器传入的是 `N - 10000` |
| C | 参数是某个偏移量，`+0x2710` 后落在 `[0, 110]` |

**最可能是 B**：脚本里 `builtin(N)` 的 N 在 `[10000, 10110]`，
但解释器在调用分派器前已经减去了基址，所以传进来的是 `N - 10000`。
那 `add eax, 0x2710` 就说不通了……

> ⚠️ **这里我还没完全想清楚。** `add 0x2710` 后 `cmp 0x6e`，
> 意味着 `[ebp+8] + 10000 <= 110`，即 `[ebp+8] <= -9890`。
> 所以 `[ebp+8]` 是**负数**，最可能是 `-(10000 - idx)`。
> 需要看调用方确认。**这是一个待验证的疑点。**

| 112 种操作码分派 | ❌ 仍未找到（这是 builtin，不是 opcode） |

## 11. ★ 分派表网络（本轮解出）

### 11.1 发现：不是一张表，而是一组

### 11.4 有效方法：字节级搜索

之前用 `md.disasm` 线性扫描**漏掉了 `0x3DF88`**，因为该位置前有数据字节，
反汇编流跳过了它。

改用**字节模式搜索**：

```python
# jmp dword ptr [eax*4 + imm32]
blob.find(bytes([0xFF, 0x24, 0x85]))   # 找到 95 处
```

| 寄存器 | 字节模式 | 处数 |
|---|---|---|
| `eax` | `ff 24 85` | 95 |
| `ecx` | `ff 24 8d` | 10 |
| `edx` | `ff 24 95` | 5 |
| `esi` | `ff 24 b5` | 2 |

**教训**：找跳转表不能只靠 `md.disasm` 线性扫描——数据混在代码段里会让
反汇编器跳过部分指令。字节模式搜索更可靠。

## 12. ★★ 操作码语义（本轮突破）

### 12.1 关键发现：payload 里直接含可读字符串

**不需要找分派器也能读出语义**——带名字参数的指令，payload 就是明文。

全量统计（114 个 `.ecl`）：

| opcode | 总数 | 带字符串数 | 样例 | 语义 |
|---|---|---|---|---|
| **300** | 177 | **177 (100%)** | `Ecl_EtBreak2_ni` | **按名字调用子程序** |
| **16** | 128 | **128 (100%)** | `Wave01Loop` | **跳转到标签** |
| **30** | 78 | **78 (100%)** | `WaveENID :%d` | 标签 / 格式化字符串 |
| **1006** | 76 | **76 (100%)** | `FairyWave Type 2way` | 注释 / 描述 |
| **11** | 64 | **64 (100%)** | `Wave01Sub01` | 定义标签 |
| **304** | 53 | **53 (100%)** | `Wave01_GirlA01` | 调用变体 |
| **15** | 43 | **43 (100%)** | `ItemCarryLilyAt0` | 标签引用 |

**共 13 种 opcode 带字符串参数，其中 7 种 100% 带。**

### 12.2 指令结构（已解出）

```c
struct NamedInstruction {
    uint16 id;        // 操作码（指令头）
    uint16 size;      // 总长度
    uint16 rank;
    uint16 argc;
    // payload:
    uint32 field1;    // 见下
    uint32 strlen;    // 名字长度（含 NUL，补齐到 4）
    char   name[];    // NUL 结尾，补零到 4 字节对齐
    uint8  args[];    // 后续参数
};
```

### 12.3 实测样本

**`opcode 300`（调用子程序）**：

```
size=56  raw=08000000 10000000 "Wave01_GirlA01" 000000 80bf0000 00c20000 0000e803 00001400 00000000
         |        |         |                    |       |        |        |        |
         field1=8 strlen=16 name(14+1→16)          args: float/int 混合
```

验证：`"Wave01_GirlA01"` 长度 14，`14+1=15`，补齐到 **16** ✓ 与 `strlen` 完全一致。

**`opcode 16`（跳转）**：

```
size=36  raw=00000000 0c000000 "Wave01Loop" 0000 01000000 00000000
         |        |        |
         field1=0 strlen=12 name(10+1→12)
```

验证：`"Wave01Loop"` 长度 10，`10+1=11`，补齐到 **12** ✓

### 12.4 `opcode 30` 是格式化字符串

样例：`WaveENID :%d`

**含 `%d` 占位符**，说明 ECL 支持类似 `printf` 的调试输出。
这与 TH18 的 ECL `print` 指令行为一致。

### 12.5 意义

**这绕过了「找不到 opcode 分派器」的障碍。**

之前我一直在找 112 种 opcode 的分派表，尝试了：

| 尝试 | 结果 |
|---|---|
| 搜 `cmp reg, 1023/1024` | 0 处 |
| 搜 `cmp reg, 42`（最高频） | **0 处** |
| 搜 `cmp reg, 91` | 0 处 |
| 7 处分派表逐个检查是否覆盖 42 | **全部不覆盖** |
| 搜 `movzx ..., word ptr [reg]` 循环 | 1 处，无关 |

**结论：`1..91` 区间的 opcode 不走跳转表**，可能用虚函数、二分查找或哈希。

但**这不妨碍理解语义**——从 payload 的数据特征就能读出关键指令的含义。
