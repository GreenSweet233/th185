# TH185 ECL 脚本格式（SCPT / ECLH）

> 状态：**容器结构与指令流已完全解出；81 种操作码的语义未解。**
> 日期：2026-11-11

---

## 1. 概览

`th185.dat` 里有 **114 个 `.ecl`** 文件，使用 **SCPT** 容器格式——
这正是 TH18 及之后作品的 ECL 格式，与 thcrap 的 `ThModern_ECLGetSub` 一致。

```
.ecl (SCPT)
  ├─ 头部（魔数 + 版本 + 名字数 + 子程序数 + 段标记）
  ├─ 子程序偏移表（34 项）
  ├─ 名字表（明文 ASCII）
  └─ 每个子程序：ECLH 块
       └─ 指令流（[id][size][rank][argc][payload]）
```

---

## 2. SCPT 容器

### 2.1 头部

```c
struct ScptHeader {
    char     magic[4];      // +0x00  "SCPT"
    uint32   version;       // +0x04  0x00100001
    uint32   name_count;    // +0x08  default.ecl = 36
    uint32   reserved0;     // +0x0C
    uint32   sub_count;     // +0x10  default.ecl = 34
    uint32   reserved1;     // +0x14
    uint32   reserved2;     // +0x18
    uint32   reserved3;     // +0x1C
    uint32   reserved4;     // +0x20
    char     anim_tag[4];   // +0x24  "ANIM"
    uint32   reserved5;     // +0x28
    char     ecli_tag[4];   // +0x2C  "ECLI"
    uint32   reserved6;     // +0x30
    uint32   sub_offsets[sub_count];  // +0x34
    // 随后是名字表（NUL 结尾字符串）
};
```

## 3. ECLH 子程序块

### 3.1 结构

```c
struct EclhBlock {
    char     magic[4];      // +0x00  "ECLH"
    uint32   header_size;   // +0x04  16
    uint32   reserved0;     // +0x08
    uint32   reserved1;     // +0x0C
    uint32   reserved2;     // +0x10
    // +0x14（tag 后 20 字节）开始是指令流
};
```

### 3.2 指令格式

```c
struct Instruction {
    uint16 id;      // 操作码
    uint16 size;    // 含本头的总长度
    uint16 rank;    // 推测：执行层级 / 优先级
    uint16 argc;    // 推测：参数个数
    uint8  payload[size - 8];
};
```

最初以为偏移表固定在 `+0x34`，结果**只有 `default.ecl` 能解析**。


## 9. ★ 内置函数表（本轮重大发现）

### 9.1 位置

**VA `0x43ECF4`**（`.text` 段内），**117 项**函数指针。

这是 ECL 解释器的**内置函数分派表**：脚本调用 `builtin(N)` 时，
解释器查表跳到第 N 个 thunk 执行。

### 9.2 调用约定

全部是 `__thiscall`：`ecx` = ECL 上下文对象指针，返回值在 `eax`。

绝大多数 thunk 是**纯字段读取器**，所以这张表同时是 **ECL 上下文布局图**。

## 10. ★ 内置函数分派器（本轮解出）

### 10.1 分派代码

**RVA `0x3E586`**：

```asm
03E586: mov eax, dword ptr [ebp + 8]      ; builtin 索引参数
03E589: sub esp, 8
03E58C: add eax, 0x2710                   ; ★ 基址 10000
03E591: cmp eax, 0x6e                     ; ★ 上限 110
03E594: ja 0x3ecea                        ; 超限 -> 返回 0
03E59A: jmp dword ptr [eax*4 + 0x43ecf4]  ; ★ 跳转表
```

### 10.2 关键结论

| 项 | 值 |
|---|---|
| builtin 编号基址 | **10000**（`0x2710`） |
| builtin 编号上限 | **10110**（`10000 + 110`） |
| 有效 builtin 数 | **111** |
| 表索引 | `N - 10000` |
| 表总项数 | 117 |
| 不可达项 | 111..116（超出 `cmp 0x6e` 上限） |

**表 117 项中只有前 111 项可达。** 而不可达的 111..116 恰好是
`push 2; push 2`、`push 6; push 3` 这类**成对参数辅助函数**——
它们不是 builtin，而是被其他代码直接调用。

### 10.3 这解决了一个疑问

上一轮我把表里的 117 项都当作 builtin，但索引 111..116 的实现看起来
与其余项风格不同（都是 `push imm; push imm` 而非读取字段）。
现在明白了：**它们超出 `cmp 0x6e` 的范围，本来就不是 builtin。**

### 10.4 调用链

```
ECL 脚本: builtin(10042)
     ↓
分派器 0x3E586: eax = 10042 + 10000? 不，是 eax = 42
```

等等——`add eax, 0x2710` 是**加上** 10000，不是减去。
所以参数是 **负偏移**？重新理解：

| 可能解释 | 说明 |
|---|---|
| A | 参数 `[ebp+8]` 是相对基址的**负**值（如 `-10000`），加上 10000 得 0 |
| B | 参数本身就是 builtin 编号，但解释器传入的是 `N - 10000` |
| C | 参数是某个偏移量，`+0x2710` 后落在 `[0, 110]` |

**最可能是 B**：脚本里 `builtin(N)` 的 N 在 `[10000, 10110]`，
但解释器在调用分派器前已经减去了基址，所以传进来的是 `N - 10000`。
那 `add eax, 0x2710` 就说不通了……

> ⚠️ **这里我还没完全想清楚。** `add 0x2710` 后 `cmp 0x6e`，
> 意味着 `[ebp+8] + 10000 <= 110`，即 `[ebp+8] <= -9890`。
> 所以 `[ebp+8]` 是**负数**，最可能是 `-(10000 - idx)`。
> 需要看调用方确认。**这是一个待验证的疑点。**

## 13. ★ 数值型操作码分析（本轮）

### 13.1 决定性发现：opcode 40 是子程序头部

```
子程序总数: 486
首指令为 opcode 40: 486  (100%)
其他首指令: {}
```

**486/486 全部以 `opcode 40` 开头，无一例外。** 这是 ECL 的 `sub` 声明。

`[1]` 的取值只有 8 种：`0, 4, 8, 12, 16, 20, 24, 28`（步长 4）。
与子程序的指令数**无关**（0/486 吻合），所以它是**属性标记**而非计数。

分布：`0`×251、`8`×80、`4`×52、`16`×42、`24`×28、`12`×19、`20`×9、`28`×5。

### 13.2 opcode 44 是角度参数（弧度）

float 解读下值域全部是 **π 的分数倍**：

| 值 | 弧度 | 角度 |
|---|---|---|
| `-1.5708` | `-π/2` | -90° |
| `-2.3562` | `-3π/4` | -135° |
| `-0.0873` | `-π/36` | -5° |
| `0.0524` | `π/60` | 3° |
| `0.1745` | `π/18` | 10° |
| `0.3491` | `π/9` | 20° |

**这是弧度制角度参数**，`opcode 44` 是「设置角度/方向」类指令。

> 注意：`-9999.0` 到 `-9958.0` 那批值是 **builtin 引用**（负值编码），
> 不是真实角度。排除它们后才是真正的角度值域。

### 13.3 各数值型 opcode 的类型判定

用「哪种解读更合理」判断 int 还是 float：

| opcode | 类型 | 值域 | 判断依据 |
|---|---|---|---|
| **44** | **float** | `-π/2 .. π/9` | 973/1009 float 合理，0/1009 int 合理 |
| 42 | int | `-10000..30000` | 2548/2549 int 合理 |
| 23 | int | `-9985..1000` | 999/999 int 合理 |
| 40 | int | `0..28` 步长 4 | 486/486 int 合理 |
| 12 | int | `44..1240` 多为 4 倍数 | 571/571 int 合理 |
| 14 | int | `-1236..-40` **全负** | 529/529 int 合理 |

**`opcode 14` 全为负数**，与 `opcode 12` 全为正数形成对照——
两者很可能是「正向/反向」一对（如 `add`/`sub` 或 `forward`/`backward`）。

### 13.4 payload 的通用结构

所有数值型 opcode 的 payload 都是 3~4 个 dword：

```c
struct NumericPayload {
    int32 field0;   // 几乎恒为 0（占位）
    int32 value;    // ★ 真正的值（int 或 float 位模式）
    int32 flag;     // 通常 0，偶尔 1 或 11
    int32 extra;    // 部分 opcode 有第 4 个字段
};
```

`flag` 的取值几乎全是 0（>99%），偶尔 1 或 11——不是类型字段，
更像「是否取负」或「变体选择」。

### 13.5 opcode 12 / 14 的配对关系

```
opcode 14 -> opcode 12:  31 次
opcode 12 -> opcode 14:   0 次
```

**单向配对**：`14` 后面可能跟 `12`，但反过来没有。
结合 `14` 全负、`12` 全正，可能是「设置负偏移」后跟「设置正偏移」。

### 13.6 opcode 40 后紧跟的指令

| 后续 opcode | 次数 |
|---|---|
| 502 | 154 |
| 1015 | 108 |
| 302 | 88 |
| 42 | 52 |
| 600 | 32 |
| 12 | 29 |

`502`/`1015`/`302` 是子程序体最常见的开头——可能是「设置初始状态」类。

## 14. opcode 12 / 14 的深入分析（本轮）

### 14.1 已确认的事实

| 事实 | 证据 |
|---|---|
| **全部值是 4 的倍数** | 12: 571/571；\|14\|: 529/529，无例外 |
| **`12 = \|14\| + 4`** | 70/71 项匹配（唯一例外是 `Ecl_EtBreak*` 系列） |
| 值域结构完全一致 | 两者相邻差都是 `4,8,12,16,20,24,28,32,36,40,44,160,192` |
| `12` 全正、`14` 全负 | 0/571 负、529/529 负 |
| `14 -> 12` 单向 | 31 次；反向 0 次 |
| `[0]` 恒为 0 | 571/571、529/529 |
| `[2]`/`[3]` 几乎恒为 0 | `[3]` 仅 4 次为 1 |

值域：`12` = `44..1240`（76 种），`|14|` = `40..1236`（71 种）。

### 14.2 排除的假设

| 假设 | 检验 | 结果 |
|---|---|---|
| 帧数 | 是否 60 的倍数 | ❌ 仅 25/571 和 9/529 |
| 字节偏移 | `位置 + 值` 是否落在子程序内 | ❌ `44` 这类值太小，指向无意义位置 |
| 连续坐标 | 值是否连续 | ❌ 离散，相邻差为 4..44 和 160/192 跳变 |

### 14.3 当前最佳推测

**`12` / `14` 是同一量的正负表示，单位为「4 的倍数」**。

范围 `40..1240`（约 `10..310` 个 4 单位）且离散量化，最可能是：

| 候选 | 理由 |
|---|---|
| **像素偏移** | 4 字节对齐、范围合理（40~1240 像素） |
| **角度（0.01 度为单位）** | 40..1240 对应 0.4°~12.4°，但太小 |
| **速度/加速度档位** | 离散量化，但 76 种档位偏多 |

> **`Ecl_EtBreak` 系列是唯一不满足 `+4` 规律的**（`12=120` vs `14=-152`，差 32），
> 这些是「弹幕中断」相关子程序，可能用了不同的参数含义。

### 12.7 一个必须说明的限制

**「操作码编号相同」不等于「语义完全相同」。**

`Op::PushInt = 42` 在两边都是「压入整数」，这个可信度高（高频 + 名字直白）。

TH185 可能扩展过（注意 `Call` 的 size 从 32 到 100 有 15 种不同值）。

验证方式：用真实 ECL 跑，看栈是否平衡、跳转目标是否都落在指令边界。

> 这是 `corroborated` 而非 `exact` 的证据等级——
> 编号一致是强证据，但语义等价需要运行时验证。

## 13. ★ 变量引用编码（EclContext）

### 13.1 为什么需要它

`StoreInt`(948 条) 和 `StoreFloat`(445 条) 需要一个「目标地址」。
上一轮把这两个都归为「缺 EclContext」而跳过，导致覆盖率只有 43.82%。

本轮解出了引用编码，`StoreInt` 完全打通。

### 13.2 ★ 引用编码规则（实测验证）

指令头第 4 个 u16 是 `param_mask`（+0x06）。它的**低 8 位**是逐参数引用掩码。

参数值本身按符号解码：

```c
if (value < 0) {
    // 引擎内置变量槽
    index = value + 10000;      // 范围 0..110
} else {
    // 栈帧内字节偏移
    // 必须是 4 的倍数，范围 0..252
}
```

**`+10000` 这个基准正好对应 dispatcher 的 `cmp eax, 0x6e`（110）**，
这是两条独立证据互相印证。

实测（`StoreInt` 的 948 个引用）：

| 类型 | 数量 | 验证 |
|---|---|---|
| builtin 槽 | 411 | 全部落在 0..110 ✓ |
| 栈帧偏移 | 537 | 全部是 4 的倍数且在 0..60 ✓ |
| 异常 | **0** | — |

### 13.3 已标注的 builtin 索引

| 索引 | 语义 |
|---|---|
| 41 | 难度 |
| 47..50 | `is_difficulty_0..3` |
| 51..54 | `EM+0x3c/0x40/0x44/0x4f44` |
| 110 | 关卡号 - 2 |

其余槽位**语义未知，读取返回 0 而不是猜测值**。

### 13.4 ★ 数据推翻了「op45 = StoreFloat」

TH11 把 opcode 45 叫 `StoreFloat`，我照搬了。**数据不同意**：

| 操作码 | payload[4] 解为引用的比例 | payload[8] |
|---|---|---|
| 43 `StoreInt` | **948 / 948 = 100%** | 恒为 0 |
| 45（TH11 叫 StoreFloat） | **137 / 445 = 31%** | 0 或 1 |
| 44 `PushFloat` | 0 / 1760 | 0 或 1 |

那 308 个「异常」值按 float 解读全部有意义：

```
0x40800000 = 4.0f
0x41400000 = 12.0f
0xC0800000 = -4.0f
```

**op45 的 payload 形状与 `PushFloat` 一致，与 `StoreInt` 不一致。**
所以 op45 在 TH185 中**很可能不是 StoreFloat**。

处理方式：**回退为 unsupported**。

> 猜一个目标地址会污染任意变量，比拒绝执行更糟。

### 13.5 `param_mask` 不足以判定参数性质

`StoreInt` 的 `param_mask` 全是 `0xFF`——看起来能用来判定「都是引用」。
但 `PushFloat`/`op45` 的 `param_mask` **也是 `0xFF`**，却存字面值。

**所以掩码只说明「这个位置可以是引用」，不说明「这个值一定是引用」。**
必须结合 payload 内容解码。

## 16. ★★ 解释器首次真实执行：发现 Python 镜像永远看不到的 bug

### 16.1 为什么这一步必须做

在此之前，解释器的验证方式是**用 Python 重写一遍同样的逻辑，然后对比**。
这只能证明「C++ 忠实地翻译了设计」，**不能证明「C++ 真的能跑」**。

本轮把解释器接进 harness，让它对真实的 87 个 `.ecl` 文件执行。
结果立刻暴露一个致命 bug。

### 16.2 bug：跳转基准错位

首次执行结果：

```
ECLRUN files=87 subs=617 clean=28 ran=28
       finished=2 returned=0 unsupported=3 faulted=23   ← 82% 失败
       instrs=143
```

诊断输出：

```
ECLRUN FAULT wave01.ecl / Wave01Loop instrs=5 depth=0
```

`Wave01Loop` 的指令序列：

```
[0] off=680  EnterFrame(0)
[1] off=700  Jump(128)
[2] off=724  Call("Wave01Sub01")
...
[7] off=848  JumpIfNonzero(-124)
```

`Jump(128)` 的目标是 `700 + 128 = 828`——这是**文件绝对偏移**。
但 harness 给解释器的 `code` 是从 `sub.instructions.front().offset`（680）
开始**重新复制**的缓冲区，长度只有 192 字节。

`pc = 828` 越界 → `Fault`。

### 16.3 修复：`code_base` 参数

```cpp
// 跳转操作数是相对当前指令的 FILE 偏移。
// 对切片缓冲区执行时必须传入切片起点。
const i64 target = i64(code_base) + i64(pc) + i64(delta);
pc = u32(u64(target) - u64(code_base));
```

修复后：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `faulted` | **23** | **0** |
| `instrs` | 143 | **100372** |
| `maxdepth` | 10 | 21 |

**执行指令数从 143 跃升到 100372——700 倍。**

### 16.4 ★ 这个 bug 为什么 Python 镜像发现不了

Python 侧的校验逻辑是：

```python
target = ins['offset'] + delta      # 用文件绝对偏移
if target in bounds: ok += 1        # bounds 也是文件绝对偏移
```

**镜像里基准是一致的**（都用文件偏移），所以永远对。
C++ 侧因为要「把子程序切出来单独跑」才引入了基准错位。

> **镜像校验的第二个盲区**：它能验证「逻辑翻译一致」，
> 但验证不了「运行时环境差异」（缓冲区切片、生命周期、内存布局）。
> 上一轮的盲区是「镜像和被测代码同源会一起错」，
> 这一轮的盲区是「镜像没有运行时概念」。

### 16.5 顺带修的两个诊断缺陷

**缺陷 1**：嵌套 `Call` 时没有合并 `first_unsupported_opcode`，
导致所有 unsupported 都报 `op=0`（哨兵值）。

**缺陷 2**：`unsupported` 只报告第一个遇到的，掩盖了后续。

修复后立刻看到真实阻塞点：`op1015` → `op78` → `op304`/`op300`。

### 16.11 教训

## 17. ★★ op300/op304 名字调用 + 一次重要的假设回退

### 17.1 op300 / op304：带名字的子程序调用

```c
struct Op300Payload {
    uint32 flag;         // 0 / 8 / 16 —— 是标志，不是前缀长度
    uint32 name_length;  // 名字区长度（含 NUL 与填充）
    char   name[];       // 恒从 payload + 8 开始
    uint32 args[6];      // 名字后恒剩 24 字节
};
```

| 操作码 | 次数 | 解析成功 |
|---|---|---|
| `op300` | 244 | **244 / 244** |
| `op304` | 53 | **53 / 53** |

### 17.2 ★ 与 `Call` 的机制不同

我最初把 `payload[0]` 当成前缀长度（因为 `Call` 是这样），结果名字被截断：

```
payload = 08000000 10000000 "Wave01_GirlA01" ...
          ^flag=8  ^nlen=16

按「名字在 8+8=16」读 -> "irlA01"   ✗
按「名字在 8」读     -> "Wave01_GirlA01"  ✓
```

| 操作码 | `payload[0]` 含义 | 名字位置 |
|---|---|---|
| `op11 Call` | **前缀长度** | `8 + prefix` |
| `op300` / `op304` | **标志**（0/8/16） | **恒为 8** |

**同一个位置的字段，在不同操作码里含义不同。**

### 17.3 ★★ 一次重要的假设回退

我观察到一批操作码的 `payload[0]` 在多数样本里是 0，就假设它们「纯数据、不操作栈」，
批量加入了 20 个。结果：

```
clean=141  ran=141  instrs=608925  faulted=5  maxdepth=1024  ← 栈溢出
```

`maxdepth=1024` 正好等于栈容量，说明栈在无界增长。

### 17.4 根因：`payload[0]==0` 不等于「无栈效果」

`Wave17_Girl_at` 的循环体（off 2372..2620）：

```
off=2372  op604                    净 +0   ← 假设它不弹栈
off=2400  op601                    净 +0   ← 假设它不弹栈
off=2420  PushInt(200)             净 +1
off=2440  PushInt(150)             净 +1
off=2460  PushInt(100)             净 +1
off=2480  PushInt(80)              净 +1
off=2500  PushInt(80)              净 +1
off=2520  PushInt(80)              净 +1
off=2540  PushInt(80)              净 +1
off=2560  PushInt(80)              净 +1
off=2580  op23                     净 +0
off=2600  PostDecrement            净 +0
off=2620  JumpIfNonzero(-248)      净 -1
```

**每轮净增 7 个栈槽。** 跑 2000 轮就溢出。

这说明 `op601`/`op602`/`op604`/`op605`/`op606`/`op607`/`op611`
**必须消费那些压入的值**——它们是「用 8 个参数设置某个东西」的操作。

### 17.5 回退：正确性优先于覆盖率

把 600 族从 record-only 列表移除后：

| 指标 | 错误假设 | 回退后 |
|---|---|---|
| `clean`（可执行子程序） | 141 | **112** |
| `faulted` | 5 | **0** |
| `maxdepth` | **1024（溢出）** | **26（健康）** |
| `instrs` | 608925 | 101657 |

**可执行子程序从 141 降到 112，但这 112 个是真正正确的。**

> 如果保留 141 个，那 29 个「能跑」的子程序实际上在静默破坏栈——
> 比直接失败危险得多。

### 17.6 另一个发现：`EnterFrame(n)` 的 `n` 不是槽位预算

`Wave17_Girl_at` 开头 `EnterFrame(4)`，随后压入 20+ 个值。
如果 `n` 是槽位预算，第 5 个压入就该失败。

**`n` 是「参数个数」**，不是容量限制。栈容量需要 16384 而非 1024。

### 17.9 教训

**「字段在多数样本里是 0」不能推出「该指令没有副作用」。**

| 错误推理 | 正确推理 |
|---|---|
| `payload[0]==0` → 纯数据 | `payload[0]==0` → **只是没有前缀** |
| 覆盖率涨了 → 进展 | **覆盖率涨了且故障为 0** → 进展 |

**栈平衡检查是最好的「假设检验器」**：
如果某个指令被误判为不弹栈，栈会单调增长，
`maxdepth` 会逼近容量——这是数据在告诉你「你的假设错了」。

这次 `maxdepth=1024`（正好等于容量）就是那个信号。

## 18. ★ 栈效果推断器：用循环约束反解未知操作码

### 18.1 动机

上一轮的教训是「误判某个操作码不弹栈会让栈无界增长」。
那么反过来：**如果我知道栈必须平衡，能不能反推出未知操作码的效果？**

### 18.2 原理

后向跳转定义了一个循环体。规范的程序里，循环体必须把栈恢复到进入时的深度：

```text
Σ (每个操作码出现次数 × 其栈净增) = 0
```

已知操作码贡献已知值，所以残差就钉住了**该循环体内未知操作码的合计贡献**。
收集大量循环就能解出单个操作码。

### 18.3 ★ 关键：必须过滤不可信约束

**第一次运行（不过滤）给出了荒谬的结果**：

```
op 81  net -17
op 82  net +15
op 603 net +15
op 604 net -9
op 535 net +9
```

**单个指令不可能有 ±17 的栈效果。** 说明有些循环并不平衡——
它们故意改变栈深度（比如用 `LeaveFrame` 提前退出）。

加上 `|残差| <= 4` 过滤后：

```
480 个含未知 op 的循环 → 404 个可信（84%）
解出 32 个操作码，全部 |net| <= 4
```

| `605` | -1 | `603` | -1 |

### 18.5 ★ 一个「不自洽」本身就是信息

`Wave17_Girl_at` 的循环：

```
推入 8 个值（8 × PushInt）
弹出 1 个（JumpIfNonzero）
已知部分净增 +7
→ 需要未知 op(604, 601) 贡献 -7
```

但推断给出 `op601 = +1`、`op604 = 0`，**合计 +1 ≠ -7**。

**这个矛盾证明该循环是「故意改变栈深」的非平衡循环**，
被 `|残差| <= 4` 过滤器正确排除。

> 推断器的价值不只是「给出答案」，
> 还在于「指出哪些约束根本不能用」。

### 18.6 局限（必须说明）

| 能做的 | 不能做的 |
|---|---|
| 给出**候选**栈效果 | 证明语义 |
| 排除不自洽的约束 | 解出所有操作码 |
| 为下一步实现提供依据 | 替代真实执行验证 |

**这些是 `observed`（有 404 个约束支撑），不是 `exact`。**
