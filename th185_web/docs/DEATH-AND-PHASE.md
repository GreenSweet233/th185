# 死亡 / 残机 / 阶段状态机 —— 原版实测证据

> 来源：本文件全部数字来自对原版 `th185.exe` 的静态反汇编（capstone，重同步线性扫描
> 覆盖 .text 全部 207,543 条指令）与 PE 字符串表扫描。
> 不是推测，不是从 TH18/TH11 搬运。
>
> 生成动机：2026-11-24 发现「玩家残机归零后关卡仍继续并显示通关」，
> 需要先确定原版行为再决定改不改。**结论是：原版确实不会因残机为 0 而结束关卡。**

---

## 1. 残机全局 `0x4D10BC` 的全部访问点

按 `[reg+disp]` 与 `[disp]` 两种寻址重同步扫描后的完整清单。
**精确计数：`.text` 内共 22 处引用** —— 6 处 `mov reg,[mem]`（读）、
2 处 `cmp`（条件读）、14 处写（其中 `dec`/`sub` 各 1 处为读-改-写）。
（6 + 2 + 14 = 22，下表逐条可数。）

| 地址 | 指令 | 性质 |
|---|---|---|
| `0x40A341` | `mov ecx,[0x4d10bc]` | 读（加命）|
| `0x40A365` | `mov [0x4d10bc],ecx` | 写（+1 后回写）|
| `0x40A371` | `mov [0x4d10bc],7` | 写（钳制到 7）|
| `0x40A42A` | `mov eax,[0x4d10bc]` | 读（加命，另一份实现）|
| `0x40A485` | `mov [0x4d10bc],eax` | 写 |
| `0x40A48F` | `mov [0x4d10bc],7` | 写（钳制到 7）|
| **`0x40AE8B`** | **`cmp dword [0x4d10bc],0`** | **读 —— 扣命前置守卫** |
| **`0x40AEC3`** | **`dec dword [0x4d10bc]`** | **写 —— 扣命（唯一带守卫的扣命点）** |
| `0x40AEE9` | `mov ecx,[0x4d10bc]` | 读（加命，第三份实现）|
| `0x40AF0C` | `mov [0x4d10bc],ecx` | 写 |
| `0x40AF17` | `mov [0x4d10bc],7` | 写（钳制到 7）|
| `0x412E38` | `mov ecx,[0x4d10bc]` | 读（加命，第四份实现）|
| `0x412E5C` | `mov [0x4d10bc],ecx` | 写 |
| `0x412E68` | `mov [0x4d10bc],7` | 写（钳制到 7）|
| `0x414D58` | `mov ecx,[0x4d10bc]` | 读（加命，第五份实现）|
| `0x414D7C` | `mov [0x4d10bc],ecx` | 写 |
| `0x414D88` | `mov [0x4d10bc],7` | 写（钳制到 7）|
| `0x444042` | `mov eax,[0x4d10bc]` | 读（HUD 显示）|
| `0x44870B` | `mov [0x4d10bc],edi` | 写（整局初始化）|
| `0x448779` | `mov [0x4d10bc],edi` | 写（整局初始化）|
| **`0x4622D6`** | **`cmp dword [0x4d10bc],0`** | **读 —— phase 2 处理器的残机分支** |
| **`0x46327B`** | **`sub dword [0x4d10bc],1`** | **写 —— 扣命（无守卫）** |

**关键结论 1：只有 8 处「读」残机**（6 处 `mov reg,[mem]` + 2 处 `cmp`），
其中**只有 2 处是条件判断**（`0x40AE8B` 与 `0x4622D6`），
其余 6 处都是「加命」或「HUD 显示」读旧值。

**关键结论 2：没有任何一处拿残机去决定「关卡是否结束」或「能否通关」。**

## 2. 扣命函数 `0x40AE70` 的完整反汇编

```asm
0040AE70  push ebp
0040AE71  mov  ebp, esp
0040AE73  mov  eax, [0x4d7c3c]      ; 全局游戏对象
0040AE79  mov  esi, ecx
0040AE7B  mov  eax, [eax+0x47fac]  ; phase
0040AE81  cmp  eax, 2
0040AE84  je   0x40AE8B            ; phase==2 → 允许
0040AE86  cmp  eax, 4
0040AE89  jne  0x40AED3            ; 不是 2 也不是 4 → 拒绝
0040AE8B  cmp  dword [0x4d10bc], 0 ; ★ 残机 <= 0 ?
0040AE92  jle  0x40AED3            ; ★ 是 → 直接返回 0，不扣命
0040AE94  cmp  dword [ebp+8], 0
0040AE98  jne  0x40AED3
0040AE9A  push 0x21
0040AE9C  call 0x417790            ; 无敌判定
0040AEA1  test eax, eax
0040AEA3  je   0x40AEB1
0040AEA5  cmp  dword [0x4d1074], 0x12C ; 弹币 >= 300？
0040AEAF  jge  0x40AED3
0040AEB1  mov  ecx, esi
0040AEB3  call 0x40ACC0            ; 爆炸 / 特效
0040AEB8  mov  ecx, [0x4d7c3c]
0040AEBE  call 0x463650
0040AEC3  dec  dword [0x4d10bc]    ; ★ 残机 - 1
0040AEC9  mov  eax, 1              ; 返回 1 = 扣命成功
0040AED0  ret  4
0040AED3  xor  eax, eax            ; 返回 0 = 没扣
0040AED7  ret  4
```

**`jle 0x40AED3` 是前置守卫，不是「归零即 Game Over」。**
残机为 0 时原版**连命都不扣了**，玩家继续存在。

## 3. phase 字段 `[gameobj+0x47FAC]` 的状态机

### 3.1 写入点（字节级扫描 `C7 /0` `mov dword [reg+disp32], imm32`）

`.text` 内对 `0x47fac` 的立即数写入**总共只有 6 处**，且写入值只有 0 / 1 / 2 / 4：

| 地址 | 写入值 | 上下文 |
|---|---|---|
| `0x460DAB` | **1** | 函数入口无条件设 1（一局开始）|
| `0x462000` | **1** | `cmp [edi+0x638],0x3c` / `jl` —— **计数器 >= 60 才恢复 1** |
| `0x46231E` | **0** | phase-2 处理器内，随后 `call 0x463920`（重置为「进行中前」状态）|
| `0x4632A4` | **2** | 扣命后进入「被弹 / 复活」状态 |
| `0x46359F` | **4** | 结算 / 通关状态 |
| `0x463696` | **1** | 小函数 `0x46367E`：设 `[+0x63c]=0x42700000`、`[+0x634]=0x3b` 后设 1 |

### 3.2 phase 值语义（由分派表与判断点共同确定）

函数 `0x461E9E` 处是 phase 分派器：

```asm
00461E9E  mov  eax, [edi+0x47fac]
00461EA4  cmp  eax, 4
00461EA7  ja   0x462396          ; >4 越界
00461EAD  jmp  dword [eax*4+0x462AA4]   ; ★ 跳转表
```

跳转表 `0x462AA4` 实测内容：

| phase | 处理器 |
|---|---|
| 0 | `0x461EB4` |
| 1 | `0x462050` |
| 2 | `0x462191` |
| 3 | `0x46237E` |
| 4 | `0x462155` |

| 值 | 语义 | 证据 |
|---|---|---|
| **0** | 进入关卡前的重置态 | `0x46231E` 写入后紧跟 `call 0x463920` |
| **1** | 正常游玩 | `0x460DAB` 开局无条件写入；`0x462000` 计数满 60 恢复 |
| **2** | 被弹 / 等待复活 | 扣命后 `0x4632A4` 写入 |
| **3** | 结算中（禁止再扣命）| `0x462CCD` / `0x463114` 都是「2/3/4 都跳过，只处理 0/1」|
| **4** | Boss 击破 / 通关结算 | `0x46359F` 写入，调用者是 `0x462CF5` / `0x462E96` / `0x463134`（即 phase 0/1 处理器走通关分支）|

> **注**：`cmp dword [reg+0x47fac], imm8` 的 5 处是 `0x44C00C`(4)、`0x44C033`(2)、
> `0x45930B`(1)、`0x462AF1`(2)、`0x46463D`(1)。**没有一处写 3**，
> 所以 phase 3 在这份二进制里从未被写入——它是被比较却不可达的分支。
> 这一点如实记录，不作解释性推测。

## 4. 残机为 0 之后原版到底做什么

phase-2 处理器（`0x462191`）的尾部是关键：

```asm
004622C7  mov  eax, [edi+0x638]     ; 死亡后计数器
004622CD  cmp  eax, 0x1e            ; >= 30 帧？
004622D0  jl   0x462396             ; 不够 → 什么都不做
004622D6  cmp  dword [0x4d10bc], 0  ; ★ 残机 < 0 ?
004622DD  jge  0x462305             ; ★ 不是 → 走正常复活
004622DF  cmp  eax, 0x1e            ; 恰好 30 帧？
004622E2  jne  0x462305
004622E4  mov  eax, [0x4d7c44]
004622E9  cmp  dword [eax+0xc], 1
004622ED  je   0x4622F4
004622EF  call 0x45F050             ; ★★★ 残机 < 0 的收尾路径
004622F4  push ecx
004622F5  lea  ecx, [edi+0x634]
004622FB  call 0x4057C0
00462300  jmp  0x462396
00462305  ...                       ; 正常复活：设 phase=0，call 0x463920
```

**这是唯一一处「残机参与决定后续状态」的地方，判据是 `残机 < 0`，不是 `== 0`。**

而 `0x40AE8B` 的守卫保证 **`take_hit` 这条路径永远不会把残机扣到负数**。
全程序只有一处无守卫扣命 `0x46327B sub dword [0x4d10bc],1`（在函数 `0x463170` 内，
该函数被 phase-4 处理器 `0x46218C` 调用），紧随其后 `js 0x4632A4`。

`0x45F050` 的内容：

```asm
0045F050  mov  edi, [0x4d7c38]
0045F056  call 0x449900
0045F061  mov  esi, [0x4d7b0c]
0045F067  cmp  dword [esi+0xd0], 1
0045F06E  jne  0x45F08F
0045F070  ...                             ; 按 [0x4d5af4] & 0x800 选 [0x4d5ab8] = 4 或 2
0045F08F  push 2
0045F091  mov  ecx, edi
0045F093  call 0x45DFB0                   ; 状态切换到 2
```

## 5. 原版有没有「Game Over」界面

**没有。** 对 `th185.exe` 全文件 ASCII 串扫描（长度 >= 4）：

| 串 | 结果 |
|---|---|
| `Game Over` / `GAME OVER` / `game over` | **不存在** |
| `GameOver` | **不存在** |
| `Continue` / `CONTINUE` | **不存在** |
| `Retry` / `RETRY` | **不存在** |
| `Failed` | **不存在** |

实际存在的相关串：`Game Start`、`Pause`、`UnPause`、`Clear`、`ExClear`、
`Extra Stage Clear`、`Stage All Clear`、`Select`、`Over Drive`（难度名）。

**因此「残机归零 → 弹出 Game Over 画面」这个模型在原版里找不到任何证据。**

## 6. 结论

1. **原版不会因为残机 == 0 而结束关卡。** `take_hit` 在残机 <= 0 时直接拒绝扣命，
   玩家继续存在、继续可以射击与移动。
2. **原版确实有「一局结束」的通路**，但它在 phase-2 处理器里，判据是 **残机 < 0**，
   且需要「死亡计数器恰好 30 帧」。这条路径通向 `0x45DFB0(2)` 的状态切换，
   **不是**我们模型里的 `Phase::Failed`。
3. **所以「0 残机仍能通关」不是本仓库引入的回归**，它至少不违反上述已测证据。
   把它当成 bug 去「修」，就等于发明原版没有的逻辑。
4. 本仓库真正的偏差在于**我们自己写了个空转分支**，而不是这个现象：
   - 旧代码在 `lives_now == 0` 时只写 `stats_.game_over = 1` 然后**什么都不做**：
     不复活、不给无敌窗、不改 phase。玩家被丢在死亡位置，阶段继续跑到「通关」。
     这既不是原版行为，本身也不自洽（既没结束也没恢复）。**已修**：现在按实测
     语义「`life >= 0` 一律复活（含 0 命）」。
   - `FrameStats::game_over` 是本仓库自造的统计字段，原版没有对应全局。
     现降级为「残机为负时才置位」的诊断量（经由 `take_hit` 不可达），
     并在代码注释里写明**任何代码都不得把它当作「本局已结束」**。
   - **仍然存在的结构差异**（未做，如实记录）：原版死亡流程是
     「`dec life` → phase=2 → 计数器满 30 帧 → 复活或收尾」，
     我们实现的是**当帧直接 `respawn()`**，没有 phase 2 这个可观察的死亡态，
     也没有那 30 帧的死亡停顿。要补它需要先确证 `[gameobj+0x638]` 的帧语义（见 §7）。
