## 1. 两种路线对比

| | 字节级 matching decomp | **功能还原重建（本项目）** |
|---|---|---|
| 目标 | 编译产物与原版**逐字节相同** | 行为与原版**等价**（同输入 → 同帧状态、同分数、同录像） |
| 编译器 | 必须锁定原版工具链与精确版本 | 任意现代编译器（Emscripten / clang） |
| 验证 | 分节 SHA-256 全等 | 内存状态快照比对 + 模块级原版函数对照 |
| 投入产出 | TH06 级别（MSVC 2002）尚可；现代 MSVC 极低 | 与编译器无关，直接服务产品目标 |
| 与 Eagler Touhou 的关系 | 产出的 exe 无法直接跑在浏览器 | 天然适配 C++ → WASM → WebGL2 |

### 为什么 TH185 选后者

**① 工具链版本不利。** TH185 的 Rich Header 显示同时存在 build **27412 / 31328 / 31332** 三档编译单元（对应 VS2019 16.x 的不同更新），且 .text 段达 711,168 字节（TH18 是 702,464）。现代 MSVC 的 LTCG、/O2 指令重排、SSE 自动向量化都会让字节级匹配变得极其脆弱。

**② 产品目标就是行为等价。** Eagler Touhou 的验收标准是「能在浏览器里玩到原版体验」——包括保留原版的一些 Bug。TH11 已经用这套方法跑通了 121 项模块回归 + 100,672 帧六面录像比对，是成熟路径。

**③ 字节级 matching 无法复用现有工作区。** TH08/TH10/TH11 全部是 C++/SDL3 → WASM 路线，共享 portable/sdl 渲染器。走 matching 就等于另起一套工具链，与工作区割裂。

## 2. 技术路线

### 2.1 整体架构

```
th185_web/cpp/game/     具名管理器（会话/战斗/资源/ANM/ECL/卡牌/商店…）
        ↓
th185_web/cpp/sdl/      平台层（输入、音频、文件、字体、图形设备）
        ↓
portable/sdl/           工作区共享 GLES 语义渲染器
        ↓
SDL3 → Emscripten → WebAssembly → WebGL2
```

### 2.2 行为依据的四个来源

| 来源 | 提供什么 | 获取方式 |
|---|---|---|
| **原版机器码** | 函数边界、控制流、常量表 | IDA / Ghidra 反汇编 th185.exe |
| **thcrap 断点表** | 已定位的关键函数入口 | base_tsa/th185.v1.00a.js（已逐点验证命中） |
| **thprac 全局变量表** | 数据结构布局 | thprac_th185.cpp 的 enum addrs |
| **内存状态快照** | 逐点状态基准 | thprac 地址表 + 调试器 dump（**Replay 已取消，见 §3.2**） |

### 2.3 验证手段（三级）

**级别 1：模块级原版函数对照（开发期）**

用 Unicorn 执行原版函数，与 C++ 实现对比返回值与内存副作用。工作区已有实现：th11_web/scripts/native/machine.mjs。

```js
// 概念示意
const machine = await NativeMachine.create(exeBytes);
const original = machine.call(0x414F20, { ecx: thisPtr, args: [cardId, 2] });
const reconstructed = cardManager.addCard(cardId);
assert.equal(reconstructed, original);
```

**级别 2：状态快照比对（验收）**

> ⚠️ **TH185 取消了 Replay 系统**（详见 §3.2），TH11 那套「原版录像逐帧比对」不可直接用。替代方案见 §3.3。

用 thprac 的地址表在关键节点 dump 原版内存状态，与重实现逐项比较：
- 自机位置、判定点、残机、Bomb、Power、资金（`0x4d106c`）、弹币（`0x4d1070`）
- 弹幕位置、速度、类型
- 敌人位置、血量、状态机
- **RNG 状态**（TH185 随机权重极大，RNG 必须逐位一致）
- **波次抽取结果**（`EnemyManager(0x4d7af4)+0x324` 权重数组、当前选中的 ECL sub）
- 终局分数、卡牌收集状态

**级别 3：浏览器端实测**

SDL3 / WebGL2 实际运行，验证音频、字体、触控、存档、录像导入导出。

### 3.2 关键难点：随机性 + 无录像

TH185 的设计核心是「重复游玩逐渐变简单」，随机权重被刻意放大（omake.txt 原文：「わざと振り幅大きくしています」）。

**问题一：RNG 必须逐位一致。**

- 包括种子生成、每帧消耗次数、取值范围。
- 波次抽取：`weights = EnemyManager(0x4d7af4) + 0x324`，模板名表在 `0x4B5D50`，**110 条上限**。
- 任何一处 RNG 调用次序的差异都会导致状态在第 N 帧后完全分叉。

**问题二：Replay 被取消，验证手段缺失。**

这是 TH185 相对 TH11 **最大的损失**：

| 层面 | 状态 | 证据 |
|---|---|---|
| 游戏层 | ❌ **取消了 Replay 系统** | THBWiki 原文：「本作取消了Replay系统。」 |
| 引擎层 | ✅ 代码仍在 | exe 字符串 `th185_%.2d.rpy`、`replay/%s`；thprac 钩子 `0x468764 = ReplayManager::OnTick` |

**推测**：ZUN 沿用了 TH18 引擎，Replay 代码未删只是 UI 入口被关掉。`.rpy` 格式大概率与 TH18 同构。

### 3.2.1 「ZUN 代码没写好所以砍了 Replay」这个说法不成立

网上有传言说 TH185 取消 Replay 是因为 ZUN 的 Replay 代码有 bug。**我查了证据，这个说法站不住脚。**

#### 反证一：小数点作从来就没有 Replay 菜单

扫描本机全部小数点作 exe 的字符串表，结果非常一致：

| 作品 | UI 字符串 `Replay` | UI 字符串 `Practice` | `demo/demoN.rpy` | `.rpy` 文件名模板 |
|---|---|---|---|---|
| th095 文花帖 | — | — | — | 有 |
| th125 文花帖DS | — | — | — | 有 |
| th128 妖精大战争 | — | — | 有 | 有 |
| th143 弹幕天邪鬼 | — | — | — | 有 |
| th165 秘封噩梦日记 | — | — | — | 有 |
| **th185 黑市** | **—** | **—** | **—** | **有** |
| th11 地灵殿（整数作） | — | — | 有 | 有 |
| th17 鬼形兽（整数作） | — | — | 有 | 有 |
| th18 虹龙洞（整数作） | **有** | **有** | 有 | 有 |

**读法**：

1. `.rpy` 文件名模板（`th185_%.2d.rpy`）**所有小数点作都有**——它只是引擎里的存档路径常量，跟功能开没开无关。
2. 真正标志「Replay 功能开启」的是 **UI 字符串 `Replay`**（主菜单里的「Replay」按钮文字）。这个串只有 th18 有。
3. **th095 / th125 / th128 / th143 / th165 全都没有这个串**——也就是说，**小数点作历来就不提供 Replay 菜单**，TH185 只是延续了这个传统。

> 注意 th11 / th17 也没有 `Replay` 这个**独立**串，但它们的 Replay 入口在别处（th11 是 `ReplayMenu.hpp` 的独立实现，th17 同理），且都有 `demo/demoN.rpy` 演示录像。判据要看组合，不能只看一个串。

#### 反证二：Replay 代码是完整保留的，只是 UI 入口被关

thprac 对 TH185 挂的 `ReplayManager::OnTick` 钩子在 **0x468764**，与 TH18 的 `REPLAY_MANAGER_PTR = 0x4cf418` 是同一套架构的延续。thprac 用这个钩子的方式很说明问题：

```cpp
// thprac_th185.cpp:183
EHOOK_ST(th185_replaymanager_on_tick_cutoff, 0x468764, 1, {
    pCtx->Eax = 3;   // 强制返回 3，跳过 Replay tick
});
```

thprac 在**开启 Force Wave（强制波次）窗口时**把这个钩子 Enable，关闭时 Disable（见 `thprac_th185.cpp:562` / `:646`）。

**这说明什么**：如果 Replay 代码真的「没写好」，thprac 根本不需要在调试功能里专门去屏蔽它——正是因为 ReplayManager **仍在正常运行并 tick**，thprac 才需要临时掐掉它以免干扰。

#### 反证三：TH185 的 Replay 取消与「随机性」是同一个设计决策

TH185 的核心机制是**波次随机**（110 条模板池）+ **黑市随机**（每波 3 次购买，卡池随机，带 Discount 判定）。omake.txt 原文：

> 「大きく違うのは攻略におけるランダムのウエイトです。……短時間で繰り返し遊ぶ事を想定して、**わざと振り幅大きくしています**。」

在这种设计下，**Replay 的语义会变得很尴尬**：

- 传统 Replay 记录的是「输入序列 + 初始种子」，重放时靠确定性复现。
- 但 TH185 的随机性分布在**波次抽取、黑市商品、Discount 判定**等多个点，任何一个点的 RNG 消耗次序变化都会让录像失效。
- 更要命的是：**黑市是在关卡中途弹出的交互界面**。Replay 要正确重放，就得把「玩家在黑市里买了什么」也编码进去——这已经超出传统 `.rpy` 格式的表达能力。

所以更合理的解释是：**不是代码写砸了，而是这个玩法和 Replay 天然不兼容，ZUN 选择不做。**

#### 结论

| 说法 | 判定 |
|---|---|
| 「ZUN 代码没写好所以砍了 Replay」 | ❌ **无证据支持**，且与小数点作传统矛盾 |
| 「小数点作历来不做 Replay 菜单」 | ✅ 五个小数点作 exe 字符串全部验证 |
| 「Replay 引擎代码完整保留，只是 UI 关闭」 | ✅ `ReplayManager::OnTick` 仍在 tick，thprac 需主动屏蔽 |
| 「取消 Replay 是随机性设计导致的取舍」 | ⚠️ **推测**（合理但无 ZUN 原话佐证） |

> **必须说清楚**：ZUN 本人**从未公开解释**过为什么取消 Replay。以上是基于代码事实的推断，不是官方说法。omake.txt 和 readme.txt 里**完全没提** Replay 一个字。

### 3.3 替代验证方案（四条，建议组合）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 状态快照比对** | 用 thprac 地址表在关键节点（每波开始/结束、BOSS 出场、符卡宣言）dump 内存状态，与原版逐项 diff | 不依赖录像 | 只能比对离散点 |
| **B. 确定性种子注入** | 用 thprac 的 Force Wave（`0x43D156`）固定波次，绕过随机，做单波次级逐帧比对 | 把 110 个模板逐个跑一遍，覆盖完整 | 需原版可控执行 |
| **C. thprac 练习数据** | `th185.sdb`（6.29 MB）可能含大量已完成关卡状态，作回归语料 | 现成数据 | 格式未公开 |
| **D. 自建 Replay** | 引擎层 ReplayManager 还在（`0x468764`），逆向 `.rpy` 结构后自己录自己放 | **恢复完整验证能力** | 前置成本高；且 TH185 的随机性可能让原版 `.rpy` 语义无法直接复用（见下方风险） |

#### 关于方案 D 的风险（你的担心是对的）

自建 Replay **有真实风险**，不能当成「逆向出格式就万事大吉」：

**风险一：原版 Replay 的语义可能不够用。**

TH185 的随机性分布在波次抽取、黑市商品、Discount 判定等多个点，而且**黑市是关卡中途的交互界面**。要让 Replay 正确重放，得把「玩家在黑市买了什么」也编码进去——传统 `.rpy` 格式（TH18 是 `ReplayStageData` + `ReplayChunk` 列表）未必有这个字段。

**风险二：你可能在重写一个 ZUN 主动放弃的东西。**

如果取消 Replay 确实是因为「玩法与 Replay 不兼容」（见 §3.2.1），那么自建 Replay 就等于**替 ZUN 解决一个他选择绕开的问题**。这不是不可能，但工作量和不确定性都比「逆向格式」大得多。

**风险三：验证闭环的鸡生蛋问题。**

自建 Replay 的用途是验证重实现。但如果 Replay 系统本身也是重实现的一部分，那「用重实现的 Replay 验证重实现」就不构成独立验证。**必须先用原版 exe 跑通，才能作为基准。**

#### 修正后的建议

**不要一上来就做方案 D。** 建议顺序调整为：

| 顺序 | 方案 | 理由 |
|---|---|---|
| **1** | **A. 状态快照比对** | 成本最低，不需要任何 Replay 支持，用 thprac 地址表就能做。先建立这个基础能力 |
| **2** | **B. 确定性种子注入** | 用 thprac 的 Force Wave 固定波次，把随机性降到可控，做单波次级逐帧比对。这是**最实用的主力方案** |
| 3 | C. thprac 练习数据 | 作为补充语料 |
| **最后** | D. 自建 Replay | 只有当 A+B 覆盖不了时才考虑。**不要作为 P0** |

> **重要**：方案 B（Force Wave）能绕过波次随机，但**绕不过黑市随机**。黑市部分仍需单独设计验证方法（例如用 thprac 的内存写直接指定商品，再比对购买后的状态）。

## 6. 与 TH18 项目的关系

TH18 是 TH185 的**前作**（TH185 是 TH18 的后日谈）。两者技术路线不同，但**前作的分析成果可以直接迁移**：

| | TH18（前作） | TH185 重建（本项目） |
|---|---|---|
| 路线 | 字节级 matching decomp | 功能还原重建 |
| 产出 | 可重编译的 `th18.exe` | C++ → WASM 浏览器版 |
| 可迁移的成果 | 地址表、函数识别、资源分析、卡牌类名 | — |
| 可复用的实现 | — | **ECL 解释器（格式完全相同）**、卡牌框架思路、ANM 格式 |

> 本机**没有独立的 TH18 项目目录**。TH18 相关的逆向参考资料统一放在 `_references/`，与 thprac 的 TH185 源码并列。

**关键结论**：TH185 使用与 TH18 **完全相同的现代 ECL 格式**（`ThModern_ECLGetSub` 确证）。这意味着如果 TH18 重建先完成，TH185 可以直接复用其 ECL 解释器，只做「波次随机 + 黑市经济 + Cost 系统 + 8 难度」四块增量。

**共同前置障碍**：`th18.dat` 和 `th185.dat` 都是 **PBG4 加密**，thtk 12 都不支持。这个问题两边都得解决。

## 7. 工作量评估

| 模块 | 相对 TH11 的工作量 |
|---|---|
| 引擎骨架（渲染/音频/输入/资源） | 0.3（大量复用） |
| ECL + 敌机 + 弹幕 | 0.4（复用 TH18） |
| **自机 + 卡牌效果（87 类）** | **0.8**（全新，最大块） |
| **波次随机 + 黑市 + 经济** | **0.6**（全新） |
| 9 场景 × 50 波次的内容编排 | 0.5 |
| 存档/成就/UI | 0.3 |
| **验证体系（无 Replay）** | **0.5**（额外成本） |
| **合计** | **~3.4** |

即：**约 3~3.5 倍于 TH11 的工作量**。若 TH11 是「121 项测试通过」的规模，TH185 大致需要 **400+ 项验收点**。

**建议**：TH185 适合作为**在 TH18 重建完成之后的派生工程**——复用 TH18 的 ECL/卡牌框架，只做四块增量。若从零起，工作量会接近 TH18 的两倍。
