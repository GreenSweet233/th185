# TH185 ECL 协程语义

> 状态：**解释器支持协程**（op23 成为真正的 yield）
> 边界：**场景主控的等待循环仍未解出**——`main` 的出口条件依赖未知语义

---

## 1. 两种执行语义必须共存

| 入口 | 行为 | 用途 |
|---|---|---|
| `run()` | **每帧从头重放** | 解码校验、栈平衡检查 |
| `run_coroutine()` | **保存 pc 与等待帧数** | 真实场景推进 |

为什么不能统一：

- 重放语义下，同一段代码执行 N 次和执行 1 次结果不同（所有记录型副作用重复累积）
- 协程语义下，栈状态必须跨帧保持，无法用于「干净重跑一次」的校验

**两个入口共用同一份 opcode 语义实现**，区别只在起点与挂起处理。

## 2. op23 的双重含义

```cpp
case EclOp::Op23Timer: {
    const u32 frames = arg_u32(payload, 0);
    context.last_timer_value = frames;
    ++context.timer_writes;
    if (out_wait && frames > 0) {
        if (out_pc) *out_pc = u32(pc) + u32(size);   // 下一条指令
        *out_wait = frames;
        return EclRunResult::Running;               // 挂起
    }
    break;                                          // 解码路径：只记录
}
```

`out_wait` 为空时行为与之前完全一致，所以解码校验不受影响。

## 3. ★ 一处赋值决定协程是否工作

```cpp
// 错误
u32 pc = 0;

// 正确
u32 pc = start_pc;
```

写错的后果：协程每帧从第 0 条重跑，`wait_frames` 递减但 `pc` 永远归零——
表现为「调度数不增长、调用数恒为 1」。

修正后：

```
f=0     sched=0   calls=1
f=500   sched=9   calls=2      ← 开始推进
f=2000  sched=12  calls=2
f=2500  sched=17  calls=2
```

## 6. ★ 真实边界：`main` 的等待循环

`world01t.ecl` 的 `main` 末尾：

```
[57] op12 Jump        -> 2688 ([59])
[58] op23 arg=1000    <- 等待 1000 帧
[59] op42 push 1
[60] op14 JumpIfNonzero -> 2668 ([58])   总是跳转
[61] op42 push 1
[62] op14 JumpIfNonzero -> 1852 ([19] CALL WorldWave01)
```

**出口在 `[62]`，但 `[61]` 只有 `[60]` 不跳转时才会到达。**

`[59] push 1` 后 `[60] JumpIfNonzero` 必然跳转，所以 `[61]` 永远到不了。

### 6.1 这说明什么

以下之一成立，但都没有证据判定：

| 假设 | 说明 |
|---|---|
| `op42` 在 `[59]` 不是「压入 1」 | 可能是压入 builtin 槽 1 的值 |
| `op1017`/`op1019` 会改状态 | 它们在循环里，可能改变 `[60]` 的判断 |
| `[57]` 的 Jump 目标算错 | 但它落在指令边界上 |

**已如实记录为已知边界，不猜测。**
