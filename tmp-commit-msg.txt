fix(game): 残机归零后的状态 —— 原版没有 Game Over，修的是我们自己的空转分支

## 先说结论（与原任务假设相反）

「0 命还能通关」**不是 bug**：原版根本没有「残机归零就结束关卡」这个逻辑。
但顺着这条线查下去，发现了一个**真实缺陷**，已修。

## 证据（静态反汇编，非推测）

对 th185.exe 做重同步线性扫描（.text 全部 207,543 条指令）与字节级
`mov [reg+disp32],imm32` 扫描，完整记录见 `th185_web/docs/DEATH-AND-PHASE.md`：

1. 残机全局 `0x4D10BC` 全程序只有 20 处访问，其中只有 **2 处**是条件判断：
   - `0x40AE8B` `cmp [0x4d10bc],0 / jle` —— 扣命前置守卫；
   - `0x4622D6` `cmp [0x4d10bc],0 / jge` —— 死亡处理器的分支。
   **没有任何一处拿残机决定「关卡是否结束 / 能否通关」。**
2. 因为 `0x40AE8B` 的守卫，`take_hit` 这条路径**永远不会把残机扣成负数**。
3. 死亡处理器 `0x462191`：`life >= 0` 走正常复活，**只有 `life < 0` 才走收尾**
   （`call 0x45F050` → 状态切换 2）。在本仓库的可达路径里，复活分支是唯一可达的。
4. 全文件 ASCII 串扫描：`Game Over` / `GameOver` / `Continue` / `Retry` / `Failed`
   **一个都不存在**。存在的是 `Game Start` / `Pause` / `UnPause` / `Clear`。
5. phase 字段 `[gameobj+0x47FAC]` 的写入点只有 6 处，值域 {0,1,2,4}；
   分派器 `0x461E9E` 用跳转表 `0x462AA4` 按 phase 分派 5 个处理器。
   **没有任何立即数写 3** —— phase 3 是被比较却不可达的分支，如实记录。

## 真正修掉的缺陷

旧代码（Application.cpp）在 `lives_now == 0` 时：

    if (lives_now == 0) { stats_.game_over = 1; }   // ← 然后什么都不做
    else { player_.respawn(); }

只写了一个统计字段，**不复活、不给无敌窗、不改 phase**。结果是玩家被丢在
死亡位置、阶段继续跑到「通关」。这既不是原版行为，本身也不自洽。

按实测语义改为：`life >= 0` 一律复活（含 0 命）；`game_over` 降级为只在残机
为负时才置位的诊断量（经由 take_hit 不可达），并注明**任何代码都不得把它当作
「本局已结束」**。

实测（同一场景、同一输入）：
  修复前：gameOverAtDeath=1，玩家停在死亡点
  修复后：gameOverAtDeath=0，y=180（回到起点），invuln=90（无敌窗恢复）

## 为什么 370+ 条断言没抓到

**因为 `browser_path_probe.mjs` 写好了却从来没有进 ci.mjs。**
上一轮专门为「导出与调用两侧各自都对、坏在中间连接处」这类缺陷写了它，
但它只被手工跑过 —— 「一次性脚本跑通了」不等于「进了门槛」。
